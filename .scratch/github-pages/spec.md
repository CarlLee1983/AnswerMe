# GitHub Pages：介紹頁與精選範例

Status: ready-for-agent

## Problem Statement

想採用 Answer Me 的人目前只能讀 README 的文字說明，看不到技能實際產出的解說長什麼樣子。這個技能的價值在於產出：有依據的文字、圖解與離線 HTML。只靠描述很難判斷它適不適合自己。repo 裡雖然有評測成品，但它們由舊版技能產生，散落在維護用的暫存目錄，來源連結指向本機路徑，有些甚至寫死維護者電腦上的絕對路徑，不能直接公開。

## Solution

在 GitHub Pages 發布一個繁體中文網站，網址採 GitHub 預設的專案網址，並填入 repo 的 homepage 欄位。網站包含一頁介紹頁與四頁精選範例：

- 介紹頁依序說明一句話定位、兩種用途（概念學習與成果審視）、範例卡片、一行安裝指令（詳細步驟連到 README），以及能力邊界。
- 四頁範例由 v0.1.3 技能重新產生：專案自我介紹、ticket_api 程式碼走讀、p 與 M 互動模型的文章式與簡報式各一。每頁標明產生時的技能版本、日期，並註明經人工核對。

網站內容放在 repo 中獨立的網站目錄，push 到預設分支且變更網站目錄時由 GitHub Actions 部署，也可手動觸發。既有檢查器新增網站防線，阻止本機路徑、斷掉的站內連結與範例頁的網路請求進入提交。

## User Stories

1. 身為考慮採用技能的開發者，我想用一句話知道 Answer Me 做什麼，以便快速判斷是否值得繼續看。
2. 身為考慮採用技能的開發者，我想看到「概念學習」與「成果審視」兩種用途的說明，以便對照自己的使用情境。
3. 身為考慮採用技能的開發者，我想直接打開技能產生的完整解說，以便親眼評估產出品質。
4. 身為考慮採用技能的開發者，我想從範例卡片得知每個範例示範哪種情境與形式，以便挑選與自己相關的範例。
5. 身為想理解陌生 repo 的開發者，我想看一份以真實 repo 為素材的專案介紹範例，以便知道技能如何沿實際流程解說系統。
6. 身為審視 agent 成果的開發者，我想看一份程式碼走讀範例，其中區分文件主張與實作行為，以便了解技能如何呈現證據落差。
7. 身為需要時序關係的讀者，我想在程式碼走讀範例中看到時序圖與快取命中、未命中、找不到的比較，以便理解技能如何依理解需求選擇圖解。
8. 身為對互動解說有興趣的讀者，我想操作 p 與 M 的互動模型，以便感受互動 HTML 的價值。
9. 身為需要對他人講述的讀者，我想看到同一份模型的簡報式版本，以便比較文章式與簡報式的差異。
10. 身為範例讀者，我想在每頁看到產生時的技能版本與日期，以便知道它反映哪個版本的行為。
11. 身為範例讀者，我想知道範例經過人工核對，以便判斷內容可信程度。
12. 身為範例讀者，我想點擊來源連結時看到範例產生當時的原始檔，以便核對行號與內容是否一致。
13. 身為範例讀者，我想知道互動模型是示意而非實測，以便不誤把數字當成量測結果。
14. 身為手機使用者，我想在窄螢幕上正常閱讀介紹頁與範例，以便不必回到電腦才能評估。
15. 身為網路不穩的讀者，我想在範例頁載入後即使斷線也能閱讀與操作，以便符合技能「單檔離線」的承諾。
16. 身為決定安裝的開發者，我想在介紹頁看到一行安裝指令，以便立即動手。
17. 身為需要完整安裝步驟的開發者，我想從介紹頁連到 README 的安裝說明，以便取得最新且唯一的步驟來源。
18. 身為考慮採用技能的開發者，我想在介紹頁看到能力邊界（目前只有繁體中文、不製作旁白影片、HTML 為單檔離線），以便避免預期落差。
19. 身為在 GitHub 瀏覽 repo 的訪客，我想在 repo 首頁的 homepage 欄位看到網站連結，以便直接前往網站。
20. 身為閱讀 README 的訪客，我想在 README 開頭看到網站連結，以便從文字說明跳到實際範例。
21. 身為維護者，我想在 README 的文件索引表看到網站目錄的說明，以便知道網站內容放在哪裡。
22. 身為維護者，我想修改網站後 push 到預設分支就自動部署，以便不必等發版才能修正錯字。
23. 身為維護者，我想能手動觸發部署，以便在設定變更或部署失敗後重新發布。
24. 身為維護者，我想只有網站目錄變更才觸發部署，以便技能或測試的提交不會造成無謂部署。
25. 身為維護者，我想在提交時被擋下含 `file://` 或使用者家目錄路徑的網站檔案，以便不會公開本機路徑。
26. 身為維護者，我想在提交時被擋下指向不存在檔案的站內相對連結，以便網站不出現斷連結。
27. 身為維護者，我想在提交時被擋下範例頁中載入外部資源的標記，以便範例維持單檔離線。
28. 身為維護者，我想讓介紹頁可以載入 Google Fonts 而不被誤擋，以便與技能預設模板採相同標準。
29. 身為維護者，我想讓暫存區中的網站錯誤不被工作目錄的修正掩蓋，以便檢查結果反映實際要提交的內容。
30. 身為維護者，我想在檢查失敗時看到出錯的檔案與原因，以便快速修正。
31. 身為維護者，我想手動執行瀏覽器檢查，以離線模式確認每頁沒有執行期錯誤、範例頁零 HTTP(S) 請求、390 px 寬度不溢出，以便捕捉靜態掃描抓不到的動態請求。
32. 身為維護者，我想讓瀏覽器檢查把截圖與結果寫到新的暫存目錄，以便檢視且不弄髒 repo。
33. 身為維護者，我想讓範例由只拿到技能與原始素材的獨立 agent 產生，以便範例代表技能本身的產出，而不是夾帶對話背景。
34. 身為維護者，我想在範例合併前親自過目，以便為公開內容把關。
35. 身為維護者，我想保留暫存目錄中的歷史評測成品原樣，以便它們繼續作為當時的證據。
36. 身為維護者，我想在技能改版時不必自動重做範例，只在模板、樣式或解說結構有明顯改變時重新產生，以便控制維護成本。
37. 身為維護者，我想讓網站外觀沿用技能的文章式模板樣式，以便網站本身展示技能的視覺風格，且不引入建置工具。

## Implementation Decisions

- **網站目錄**：在 repo 根目錄新增獨立的網站目錄，存放手寫靜態 HTML；不使用靜態網站產生器，不使用維護文件所在的 docs 目錄（其內容為內部文件，不公開），也不另開 gh-pages 分支。
- **頁面組成**：一頁介紹頁加四頁範例，共五頁。範例頁為單檔 HTML，CSS、JavaScript、SVG 與資料內嵌。介紹頁可引用網站目錄內的圖片（範例首屏截圖）與站內頁面，仍不引用網站目錄外或外部的資源（Google Fonts 除外）。
- **介紹頁**：推廣用的深色開發工具風格頁面，與範例頁的暖紙樣式刻意區隔（2026-10-05 修訂：原先沿用文章式模板，維護者看過後認為過於陽春、不適合推廣；以三個首屏原型比較後選定深色版，原型保存在 `prototype/landing-variants` 分支）。內容：定位與安裝指令（可複製）、以真實請求示範「請求 → 成品」的終端機區塊、標明「示意對照」的「一般回答 vs Answer Me」、概念學習與成果審視兩種用途、附截圖的分頁範例展示、能力邊界。只使用已核對的事實，不放虛構指標、推薦語或使用者數。安裝只放一行全域安裝指令，詳細步驟連到 README，README 仍為唯一來源。能力邊界的敘述與 ADR 0002、0003、0005 一致。裝章節，README 仍為唯一來源。能力邊界的敘述與 ADR 0002、0003、0005 一致。
- **範例產生**：每頁由一個獨立 agent 產生，只提供 v0.1.3 的技能目錄、一段使用者請求與原始素材；不提供本規格、歷史評測成品或驗收條件。素材分別為：專案自我介紹以 repo 本身為素材；程式碼走讀以 evidence 情境的 ticket_api 素材為來源；互動模型以 conditions 情境的模型素材為來源，產生文章式與簡報式各一。
- **範例標示**：每頁頁首或頁尾標明「由 answer-me v0.1.3 產生」、產生日期，以及「經人工核對」。互動模型標明為示意模型。標示由維護者在核對後加入，屬於網站外框，不改動 agent 產生的解說內文。
- **來源連結**：範例中指向 repo 檔案的連結改為 GitHub 上固定於 v0.1.3 tag 的網址；不指向預設分支。改寫連結屬於發布處理，須在核對紀錄中列出。
- **歷史成品**：暫存目錄中的評測成品不移動、不改寫，網站不引用它們。
- **部署**：新增 GitHub Actions 工作流程，觸發條件為 push 到預設分支且變更網站目錄，或手動觸發；將網站目錄原樣部署到 GitHub Pages，無建置步驟。repo 的 Pages 來源設為 GitHub Actions，homepage 欄位設為網站網址。
- **檢查器擴充**：在既有檢查函式中加入網站檢查，沿用其錯誤清單回報方式與 `--staged` 快照機制，讓 pre-commit 自動涵蓋。規則：
  - 網站目錄內任何檔案不得包含 `file://` 或使用者家目錄形式的本機絕對路徑。
  - 網站 HTML 的站內相對連結（`href`、`src`）必須指向存在的檔案；外部網址與頁內 anchor 不在此檢查範圍。
  - 範例頁不得以 `script`、`link`、`img`、`iframe` 等標記載入 HTTP(S) 資源；介紹頁只允許 Google Fonts 的 stylesheet 與字型網域。一般超連結（`a href`）不受此限。
  - 介紹頁與範例頁的區分以固定檔名約定判定，不另建設定檔。
- **README**：開頭加一行網站連結；文件索引表新增網站目錄一列。
- **檢查器邊界**：檢查器只做靜態掃描，不執行頁面、不驗證語意。

## Testing Decisions

- **好的測試**只透過公開入口觀察外部行為：給定一個 repo 樹，檢查函式回報哪些錯誤；給定一組頁面，瀏覽器實際載入時發生什麼。不測試內部的掃描函式或正規表示式本身。
- **主要接點：檢查函式。** 沿用既有檢查器測試的做法，在暫存目錄建立小型 repo 樹後呼叫檢查函式並斷言錯誤。至少涵蓋：
  - 合法網站（含介紹頁的 Google Fonts）通過。
  - 網站檔案含 `file:///Users/...` 或家目錄路徑時失敗，錯誤指出檔案。
  - 站內相對連結指向不存在檔案時失敗。
  - 範例頁以 script 或 stylesheet 載入外部資源時失敗；同一資源出現在一般超連結時通過。
  - 介紹頁載入 Google Fonts 以外的外部資源時失敗。
  - `--staged` 模式下，暫存區的錯誤不會被工作目錄的修正掩蓋，未追蹤檔案也不能滿足暫存中的站內連結。
  - 沒有網站目錄時，既有檢查行為不變。
- **輔助接點：瀏覽器檢查。** 參考既有模板瀏覽器檢查與其 CDP 輔助程式，新增網站檢查腳本：以 `file://` 與離線模式開啟每一頁，斷言無執行期例外、範例頁零 HTTP(S) 請求、390 px 寬度無水平溢出；互動範例操作主要控制項並確認結果改變。截圖與 JSON 結果寫入新的暫存目錄。與既有瀏覽器檢查相同，手動執行，不接 pre-commit。
- **語意驗收（人工）**：每頁範例由維護者對照原始素材核對主張、來源連結與示意標示，核對結果記錄在本功能目錄的驗證紀錄中。互動模型的數值須與 conditions 情境的既有驗收條件一致（50 ms 到 44 ms、三種 A/B 情境）；程式碼走讀須區分 README 的 TTL 主張與實作中沒有過期邏輯。
- **既有回歸**：檢查器變更後執行既有的檢查器單元測試；網站不改動技能模板，模板瀏覽器檢查不需重跑。

## Out of Scope

- 英文或雙語網站。
- 自訂網域。
- 靜態網站產生器、建置流程或任何新的 npm 套件。
- 每次 release 自動重新產生範例。
- 在網站上放完整安裝與更新步驟（README 為唯一來源）。
- 修改技能本身、技能模板或歷史評測成品。
- 公開評測紀錄、A/B 資料或維護文件。
- 網站流量分析、留言或其他執行期服務。

## Further Notes

- 盤點時發現的現有評測成品問題（相對或本機絕對路徑、舊版技能用語、測試留下的讀者註記）是改為重新產生範例的主要理由；這些檔案作為歷史證據保留。
- 範例鎖定 v0.1.3，但網站本身在 v0.1.3 之後才加入。範例來源連結指向 v0.1.3 tag 下的素材，因此專案自我介紹描述的是 v0.1.3 時的 repo 狀態，頁面標示需讓讀者看出這一點。
- 首次部署前需在 repo 設定中把 Pages 來源設為 GitHub Actions；這是一次性的 repo 設定變更，屬於對外可見的操作，執行前應確認。
