# Skill 如何選擇解說形式，何時交回使用者決定？

Type: grilling
Mode: HITL
Status: resolved
Blocked by: 03, 04
Part of: [把 Karpathy 的解說概念轉成可重用 skill](../map.md)

## Question

在已確認的理解目標與媒介範圍內，skill 應依哪些訊號選型、升級或簡化成果？使用者指定的形式、agent 的判斷與時間成本偏好如何協調？

## Discussion branches

- 什麼請求會觸發此 skill，哪些普通回答不需要進入此流程？自動選用與使用者明確呼叫各扮演什麼角色？
- 結構、因果、時間順序、參數探索等不同理解障礙，各用什麼形式較合適？何時單一形式足夠？
- 使用者指定形式與 agent 建議不同時如何處理？資訊不足、互動無助理解或產製成本較高時，何時先問？
- 使用者仍不理解時，如何根據困惑修改解說，而非無限制加長文字或增加媒介？何時結束？

## Resolution criteria

用代表案例確認可預期的觸發、選型、使用者覆寫、調整與停止行為，並指出仍須保留判斷空間的部分。

## Answer

使用者於本對話回覆「採用建議」，確認以下選型與互動行為。

### 啟用與簡短回答

使用者明確呼叫 skill，或要求「幫我理解、解釋運作、看懂變更」時啟用。單純查一個事實時直接簡短回答。

### 依理解障礙選型

資訊足夠時，由 agent 選擇最小而有效的形式。先給核心說明，再交付適合的成果；不要求每次都產出所有媒介。

| 理解需求 | 優先考慮的形式 |
| --- | --- |
| 定義、理由、簡單取捨 | 文字 |
| 結構、流程、因果、前後差異，例如陌生 repo 的請求流程 | 圖解 |
| 改變參數、比較情境或逐步觀察結果，且操作確實有助理解 | 互動 HTML |

這是選型準則，保留依具體內容判斷的空間；使用者明確指定的形式優先於預設選型。

### 何時詢問

資訊足夠時直接選型，不為例行媒介選擇追加確認。缺少關鍵資訊、需要改變使用者的明確要求，或新增付費服務時，才先詢問。工具不可用時，沿用[媒介範圍決策](04-media-scope.md)的較簡單替代形式；若替代會改變使用者明確要求，適用前述詢問條件。

### 調整與停止

依使用者指出的困惑，改用具體例子、局部圖解或操作示範。完成當次要求就交付；遇到資訊缺口則明確指出。使用者沒有追問，不等於已經理解。

實際媒介製作如何運用既有能力，由[新 skill 自己負責什麼，如何運用既有能力？](06-skill-boundary.md)決定；內容與成果是否有效的驗收方式，由[如何驗證解說可信，而且達到理解目標？](07-evidence-and-validation.md)決定。
