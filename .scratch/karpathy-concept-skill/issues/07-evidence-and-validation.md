# 如何驗證解說可信，而且達到理解目標？

Type: grilling
Mode: HITL
Status: resolved
Blocked by: 03, 04
Part of: [把 Karpathy 的解說概念轉成可重用 skill](../map.md)

## Question

概念學習與成果審視各需要哪些證據與驗收方式，才能辨別內容正確、成果可用與人實際理解？哪些可由 agent 檢查，哪些只能由使用者回饋判斷？

## Discussion branches

- 原文不可取得、材料不完整、來源相互矛盾，或 agent 只聲稱工作成功時，怎麼保留來源、假設與不確定性？
- 示意資料、簡化模型與實際觀測結果如何區分？如何讓圖像或動畫保留重要限制？
- 各首版媒介的檢查：敘述與來源一致、圖中關係正確、HTML 可離線開啟且互動確實影響結果。需要哪些可觀察的通過條件？
- 依已定案的技能邊界，如何檢查可選製作能力回傳的成果仍符合語言、證據與離線交付要求？遇到跨媒介失真或不相容成果時，什麼情況應修正或依既定規則改用替代形式？
- 如何取得不造成負擔的理解回饋？成果通過結構／執行檢查後，能聲稱什麼、還不能聲稱什麼？
- 哪些代表案例、失敗案例與通過條件，足以交給後續 skill 作者作行為驗證？

## Resolution criteria

使用者確認證據處理原則、媒介驗收條件與兩種用途的代表驗證案例；區分機器檢查與人類理解回饋。正式產製與執行這些測試留給後續建立 skill 的工作。

## Answer

使用者於本對話回覆「採用建議」，確認下列驗收規則。這張票確定規則與案例；實際試做和測試留到建立 skill 時執行。

### 內容依據

關鍵結論須能追溯到原文、程式位置或測試紀錄。解說區分事實、推論與示意；來源缺失或矛盾時明確說明。Agent 自稱成功，不直接當成驗證通過。

### 成果檢查

| 形式 | 檢查與通過條件 |
| --- | --- |
| 文字 | 核對主要主張、術語與限制，解說須與可查核的來源一致。 |
| 圖解 | 核對節點、關係與流程方向，並確認圖能正常呈現。 |
| 互動 HTML | 實際離線開啟並操作，控制項須產生符合說明的結果。 |

由可選技能製作的成果也適用同一標準，並保留[媒介範圍決策](04-media-scope.md)的語言與交付要求。未實測的部分標明；發現問題先修正，必要時依[既定替代與詢問規則](05-selection-behavior.md)調整形式。沒有執行相應檢查，不聲稱該檢查已通過。

### 理解回饋

需要時附一個可選的預測或判斷問題，例如「這個步驟失敗，會影響哪裡？」讓使用者自行確認理解。使用者的回饋用來調整解說；成果檢查通過只代表已完成相應檢查，不等於已證明使用者理解。沿用已確認的停止行為，不因使用者沒有追問便推定已理解。

### 建立 skill 時的代表驗證案例

| 情境 | 可觀察的驗證重點 |
| --- | --- |
| 閱讀陌生 repo | 說清主要流程，解說與圖中關係能對照實際程式。 |
| 審視 agent 變更 | 說清 diff、修改理由及測試證據，區分已測與未測。 |
| 互動解說 | 修改參數後結果符合說明，且 HTML 可離線開啟與操作。 |
| 來源不足 | 明確標示資訊缺口，不補造來源或將推論冒充事實；按既定規則詢問或限縮解說。 |
| 可選技能缺席 | 核心按既定規則選用替代形式；若會改變使用者明確要求則先詢問。 |
| 成果無法離線運作 | 檢查能識別問題，先修正或按既定規則處理；不可標為離線驗收通過。 |

原地圖中「試解說可能暴露理解障礙」的未知，由上述代表案例與理解回饋機制承接。使用者已確認實際試做屬後續建立 skill 的工作；試做發現的具體問題在該階段修正，不需要在本輪先製作解說成果才能完成規劃。
