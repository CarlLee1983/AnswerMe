快取從 dict 換成有 TTL 的 TicketCache

這次變更新增 cache.py 的 TicketCache，讓 TicketService 不再直接讀寫自己的 dict，而是呼叫 cache.get／cache.put。快取項目因此有了預設 60 秒的有效期限；handle_get 與 FakeRepo.find 的呼叫方式不變。

核心結論

程式碼支持 agent 的前兩點：快取確實抽到新模組，預設 TTL 是 60 秒，README 的「60 秒後過期」在預設設定下與程式一致。第三點「既有測試仍通過」只得到部分支持：test-output.txt 沒有交代測的是哪一版程式，而且兩個既有測試都不涉及過期，所以它們無法證明 TTL 有效。

我另外在暫存副本套用 diff 重跑測試，並用可控時鐘做了一次過期探測：2 個測試通過，第 60.0 秒時確實重新讀 repo。過期是「讀到時才刪」，從未再被讀取的項目會一直留在記憶體。

我實際重跑的結果（本次觀測）

2026-10-12 在本機 Python 3.14.7，把 ticket_api 複製到暫存目錄後以 git apply 套用 diff（兩個檔案都乾淨套用），之後刪除暫存目錄。結果如下：

  • 變更前與變更後執行 python3 -m unittest -v，兩者都是 Ran 2 tests … OK。
  • 用可控時鐘探測過期：第 0 秒讀取、第 59.9 秒再讀時 repo.reads 仍為 1（命中）；第 60.0 秒再讀變成 2（過期、重新查 repo）。
  • 未傳 cache 時，TicketService 的預設快取 ttl 為 60。
  • 第 0 秒存入 A、第 100 秒存入 B 且不讀 A，A 仍留在 entries 中。

這些是一次性的手動探測，不是 repo 內的測試，所以之後改動程式時不會自動防止 TTL 失效。

缺口與限制

  • 沒有過期測試（事實）：repo 中的測試不會偵測 TTL 被改壞。clock 已可注入，加一個推進假時鐘的測試是直接的補法；這是建議，本次未修改任何程式。
  • 過期項目可能累積（推論，已用上面的探測確認單一情境）：只有被再次讀取的過期項目會被刪除。若大量不同 ticket 只被讀一次，entries 會一直成長。實際影響取決於流量型態，來源沒有相關資料。
  • cache or TicketCache() 依真假值判斷（推論）：若呼叫端注入的快取物件在空的時候被視為 false（例如自訂了 __len__），建構子會悄悄改用新的 TicketCache。TicketCache 本身沒有定義 __len__，目前不受影響；寫成 cache if cache is not None else … 才不依賴這點。
  • 測試紀錄的條件不明：test-output.txt 沒有 Python 版本、執行目錄或對應 commit；本頁的重跑結果是另一次執行，不能回推原紀錄的條件。
