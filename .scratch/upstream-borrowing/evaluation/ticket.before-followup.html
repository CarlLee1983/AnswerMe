TICKET API · 呼叫流程

一張票，第一次與第二次怎麼讀？

入口是 TicketService.handle_get(ticket_id)。它先呼叫自己的 get_ticket；只有查不到這個 service 實例的 cache 時，get_ticket 才會呼叫 FakeRepo.find。

先記住這三件事

首次讀到存在的票：repo 讀取一次、存入 cache、回覆 200。同一實例再次讀同一張票：直接從 cache 回覆 200，repo 不再被呼叫。找不到票：get_ticket 丟出 NotFound，由 handle_get 轉成 404, {"error": "not found"}。

  • 誰先呼叫誰
  • 首次與再次讀取
  • 找不到票

首次與再次讀同一張票

比較的前提是同一個 TicketService 實例、同一個 ticket_id，而且第一次 repo 找得到票。cache 是實例上的字典，初始值為空。

找不到票時，誰把錯誤轉成 404？

若 cache 沒有該 ID，get_ticket 仍會呼叫 FakeRepo.find。rows.get(ticket_id) 找不到時回傳 None；get_ticket 因此丟出 NotFound(ticket_id)。外層的 handle_get 捕捉這個例外，回覆 (404, {"error": "not found"})。

找不到的 ID 不會寫入 cache。因此，在同一實例中重複查詢該 ID，依程式流程每次都會呼叫 repo，reads 也會再加 1；現有測試只檢查單次找不到的回覆，沒有測這個重複情境。

依據：service.py 第 9–11、18–31 行；單次 404 測試見 test_service.py 第 12–14 行。

來源與邊界

  • service.py 是本文執行路徑的依據；test_service.py 提供兩項行為檢查。從該目錄執行 python3 -m unittest -v，兩項測試通過。
  • README.md 說 cache 會在 60 秒後過期；目前 service.py 只有字典查詢與寫入，沒有時間欄位或過期判斷。本文按程式實際路徑解釋，不能把 60 秒過期視為已實作。
  • repo 是 FakeRepo，其 find 只從記憶體中的 rows 查找；本文不推論真實資料庫或 HTTP 框架的行為。
